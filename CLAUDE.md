# CLAUDE.md for JIT-VP: RQ1 open coding

## What this is

RQ1 of a JIT vulnerability prediction project on ClawHub skill versions. Each pair is two consecutive versions of an AI agent skill. You see the author's changelog and the diff.

We use open coding, following a thematic analysis approach: open codes per key point, then subthemes, then themes. There are **no predefined categories**. Codes and themes must come from the data. Two human coders review everything you produce.

Repo: github.com/amm4ra/JIT-VP (local folder: aise/project)

## Working across sessions

## Step 1: open coding, one round at a time

For each pair, read the changelog and the diff. Break the change into **key points**: one key point per separate change (usually 1 to 5 per pair).

For each key point, write:
- `open_code`: a short phrase (about 3 to 8 words) in your own words saying **what changed**. Concrete, not "update" or "improvement".
- `direction`: `added`, `removed` or `modified`.
- `evidence`: the file and a very short quote or description from the diff.
- `stated_motive`: only if the author says **why** in the changelog or diff (e.g. "to fix scanner warnings", "deprecated"). Otherwise leave empty. Don't guess.

Pair-level flags (one value per pair, repeat on each of its rows):
- `changelog_mismatch`: `yes` if the changelog claims a specific change that is not in the diff; `generic` if the changelog states no checkable change (release labels, auto-sync messages, vague wording, whole-skill feature summaries); else `no`. Claims about `skill-card.md` or `_meta.json` count as `no`.
- `no_author_change`: `yes` if the diff has no author changes. Then write a single key point with `open_code` = `no author change`.

Guidance:
- Describe changes **neutrally**. Don't frame them as security-related unless the change itself is clearly about security.
- There is **no target number of codes**.
- **Constant comparison:** before writing a new code, check `code_list.md`. If an existing code describes the same kind of change, reuse its exact wording. Only create a new code when none fits.
- If an earlier code was too broad or too narrow, rename or split it, update earlier rows in `open_codes.csv` to match, and record the change in `code_list.md`.
- If a diff is very long, focus on SKILL.md and added or changed scripts, and note `trimmed` in `evidence`.

`open_coding/open_codes.csv` columns:
`pair_id, round, key_point_no, open_code, direction, evidence, stated_motive, changelog_mismatch, no_author_change`

## Step 2: after each round

1. Update `code_list.md`: every distinct open code with a one-line definition, the round it first appeared, and a count of pairs. Below it, keep a **provisional grouping** of codes into subthemes (one-line definition each). Adjust the grouping as new codes come in.
2. Append one line to `saturation_log.md`:
   `round | pairs coded | key points | new open codes | new codes % | new subthemes | codes renamed or merged | no author change | changelog mismatch`
   "New" means not present in any earlier round, after merging synonyms.
3. Give me a 3-line summary, then continue with the next round unless I said to stop.

## Step 3: saturation

Saturation = **2 rounds in a row that meet both conditions** (after Guest et al. 2020):
1. no new subthemes (new open codes are allowed only if they fit existing subthemes), and
2. new open codes in the round are **under 5%** of all distinct open codes so far (cumulative, after merging, including that round).

Record the "new codes %" for every round in `saturation_log.md`. Rounds 1 to 3 always count as development rounds, so don't call saturation before round 4.

- If saturation is reached by round 6, go to Step 4.
- If not, stop after round 6 and tell me how many more rounds you think are needed. I'll draw them in `rq1_sampling.ipynb` myself. Never run the draw cells.

## Step 4: build themes bottom-up

Only after saturation:

1. Finalise the subthemes, then group subthemes into **themes**. Let the groups come from the codes.
2. Write `themes.md`. For each theme:
   - name and a one-line definition
   - its subthemes, each with a definition, "use when" and "don't use when" lines, and the open codes it contains
   - number of pairs per theme and subtheme, overall and per round
   - 2 example `pair_id`s per subtheme
   - direction split (added / removed / modified)
3. Also in `themes.md`:
   - open codes that didn't fit any group
   - groups of `stated_motive`, with pair counts
   - counts of `changelog_mismatch` and `no_author_change`
   - the subtheme saturation table from `saturation_log.md`
   - groupings you were unsure about, and boundaries between subthemes that were hard to call
4. Write `review_list.md` for the human coders: every subtheme with 3 example key points, every key point you were unsure about, every rename or merge you made, and the hardest boundaries.

## Step 5: log and stop

Append to `coding_log.md`: date, model name, the exact prompt I gave you, files read, and all renames and merges.

Then stop and give me a short summary: pairs coded, distinct open codes, subthemes, themes, the saturation table, and top stated motives.
